# Исправления модели и продолжение экспериментов

## Что изменилось по существу

- Очередь хранится для каждого ключа. Обслуживание пропорционально накопленной работе внутри шарда; запросы не исчезают при смене размещения. Это fluid-модель, не FIFO и не измерение p99 latency.
- Миграция переносит снимок и последующие записи изменяющихся ключей с ограниченной скоростью. До завершения используется старое размещение; затем происходит переключение на границе интервала. Отмена/новый перенос до завершения запрещены.
- Во время переноса оплачивается максимум старого и нового числа серверов, а копирование снижает мощность обслуживания. Остатки очереди и переноса видны и дополнительно оценены в конце горизонта; это модельная терминальная цена, не точная стоимость полного дренирования.
- В работе различаются get, set и объём сообщённых в трассе байтов. Семантика: get=1, set=2, байты/4096. Это сценарные веса, а не измерения CPU.
- Все политики начинают с 4 шардов, одинакового восстановленного инвентаря и пустой очереди. Размер базы взят из прошлых записей/TTL; очередь до момента развёртывания неизвестна и не восстанавливается.
- Q-learning и DQN_matched видят в точности одни и те же 10 дискретных признаков. DQN_continuous — отдельная абляция представления. Одинаковы действия, цель, число кандидатов, seed, переходов и проверок validation. Время вычислений раскрыто отдельно.

## Протокол и независимая оценка

Весь cluster7 считается development. Обучение — три суточных окна часов 24–96, validation — три следующих дня. Это не независимые кластеры и не rolling-origin CV: общий train предшествует трём validation-окнам. Каждый запуск обучается с нуля, 80 эпизодов по 96 шагов; 4 настройки × 3 независимых инициализации. Только финальный checkpoint. Настройка выбирается по средней стоимости трёх seed на трёх окнах, для основного результата заранее выбран seed 7. Все seed выбранной настройки опубликованы в таблицах.

До скачивания новых трасс зафиксированы код, протокол и веса в `v2_results/frozen.json`. Выбраны cluster10, cluster26 и cluster45 исключительно по малому размеру файлов архива. Для каждого первые 24 часа используются только для локальной калибровки мощности/полосы и восстановления инвентаря. Затем оцениваются следующие 144 часа без настройки весов или порогов. Это перенос с разрешённой калибровкой среды, не полностью zero-shot задача. Неподдерживаемые операции вызывают явное исключение целого кластера, без подмены другим.

Три кластера не дают надёжного доверительного интервала обобщения; общий источник может создавать зависимости. Отчёт содержит отдельные результаты каждого кластера, не притворяется исследованием всей популяции.

## Дополнение к загрузчику и вычислениям

Первый запуск отклонил cluster10 (первый запрос на секунде 1) и cluster45 (операция add). После исправления первого требования в cluster10 также обнаружились add/gets. До получения показателей политик для этих двух кластеров оформлено дополнение: gets читается как get, add создаёт объект только при отсутствии в восстановленном состоянии; успех неизвестен, это сценарное допущение без eviction. Работа попытки add стоит 2 единицы независимо от результата; байты в инвентарь и журнал идут только при модельном успехе. Основание: https://docs.memcached.org/protocols/basic/. Веса и выбор политик не менялись, первоначальные отказы сохранены. Поэтому это расширенная оценка с документированным изменением загрузчика, а не буквально неизменный протокол для всех трёх кластеров.

Плотный расчёт был остановлен во время анализа чувствительности из-за расхода памяти. Ключи сгруппированы по полному вектору JCH-размещения для 2–8 шардов: максимум 128 групп. При пропорциональном обслуживании и одинаковом маршруте суммарная очередь эквивалентна сумме очередей ключей. Максимальная нагрузка одного ключа сохраняется отдельно. Тесты проверяют эквивалентность; все 11 готовых полных траекторий cluster10 совпали с компактным исполнением в пределах округления. Параметры и метрики не изменены.

## Что остаётся ограничением

Это всё ещё симулятор кеша, а не ClickHouse. Мощность определяется средней работой и целевой средней загрузкой 65%; bandwidth — средний по медиане живой объём/8, влияние копирования — 20%. Эти числа объявлены сценарными, а не взяты из производства. Есть повторная оценка замороженных политик при мощности и полосе ×0.5 и ×2; она не служит выбору победителя.

Источники не сообщают успех операций, eviction, полный исходный инвентарь и реальную стоимость get/set. Используется last-write-wins и TTL. Для переносимых ключей полный поток записей добавляется в журнал миграции, даже при последующем истечении TTL: это консервативная аппроксимация. Затраты копирования распределены равномерно по исходным серверам, сетевой топологии нет.

Горячий ключ теперь измеряется непосредственно по интервалам, а не выводится из суммарной доли top20. Но набор действий по-прежнему только ±1 шард/сохранить; репликации и дробления ключа нет. Поэтому неснимаемая данным набором действий очередь — ограничение задачи. Гарантии нулевой очереди нет. Результаты по ключам и сдвигу нагрузки сохранены отдельно.

Представление matched одинаково, но дискретизация сама по себе может быть слабой. Небольшой бюджет обучения не доказывает предельную способность ни одного алгоритма. Неудачные seed не исключены. Новые трассы после этого отчёта уже просмотрены: дальнейшая настройка по ним потребует ещё одного holdout.

## Воспроизведение

```sh
python -m unittest v2.test_environment v2.test_pipeline -v
python -m v2.prepare data/cluster7.sort.sample100.zst data/cluster7
```

Для точного повторения изолированного запуска смотрите `v2/README.md`; команда обучения защищена от перезаписи замороженного запуска. Ноутбук читает сохранённые результаты, не переобучает модель и не открывает holdout повторно.

Источники данных: [Twitter cache-trace](https://github.com/twitter/cache-trace), [архив CMU](https://ftp.pdl.cmu.edu/pub/datasets/twemcacheWorkload/open_source/sample100/). Авторы: Juncheng Yang, Yao Yue, Rashmi Vinayak; CC BY 4.0.

## Защита от невыполнимого переноса: отдельный post-holdout эксперимент

После наблюдения зависшей миграции в cluster26 добавлена общая проверка перед началом переноса: средний поток записей за четыре прошлых интервала должен быть меньше 80% полосы, оценённое время копирования — не более восьми интервалов. Иначе команда отклоняется. Модели не переобучаются. Это адаптивное исправление после просмотра holdout, его результаты НЕЛЬЗЯ выдавать за независимое подтверждение. Правило может отклонить полезный перенос; будущие всплески и зависшую активную миграцию оно не гарантирует обработать.
