# Twitter: шардинг и обучение с подкреплением

Учебный исследовательский проект: реальные запросы Twitter → JCH → симулятор стоимости → baseline → табличный Q-learning → нейросетевой Double DQN → честная оценка.

## Как открыть

Откройте эту папку в VS Code. Выберите ядро `.venv/bin/python`. Выполненные ноутбуки уже содержат выводы и графики:

1. `01_data_overview.ipynb` — происхождение, колонки, качество данных, распределение нагрузки и механика JCH.
2. `02_simulation_and_baselines.ipynb` — модель, тесты, фиксированные стратегии и пороговый baseline.
3. `03_q_learning.ipynb` — обучение и подбор параметров табличного агента.
4. `04_neural_dqn.ipynb` — настоящая нейросеть, поиск гиперпараметров, сохранённые веса и обучение.
5. `05_comparison.ipynb` — финальный test, разложение стоимости, изменение числа шардов, чувствительность к seed.

По умолчанию ноутбуки 03/04 загружают готовые результаты. Для повторного обучения передайте `retrain=True`. Для полного воспроизведения с нуля: `python data_pipeline.py`, затем `python experiments.py`, затем выполните ноутбуки. Смена данных/симулятора требует нового каталога результатов: не используйте старые модели и кэш. В `results/protocol.json` записаны протокол, хеш обработанных данных и параметры. При повторных исследованиях не используйте уже просмотренный test для настройки.

Установка в новой папке:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m jupyter lab
```

`zstd` должен быть установлен для подготовки исходника (на данном Mac доступен). Веса обучаются в NumPy; PyTorch, GPU и облачные сервисы не требуются. Ядро Jupyter при выполнении через VS Code выбирайте из этой папки.

## Источник и границы интерпретации

Данные — анонимизированные запросы к кеширующему кластеру, не твиты. Исходный проект: https://github.com/twitter/cache-trace. Авторы: Juncheng Yang, Yao Yue, Rashmi Vinayak. *A large scale analysis of hundreds of in-memory cache clusters at Twitter*, OSDI 2020: https://www.usenix.org/conference/osdi20/presentation/yang. Данные и документация распространяются под CC BY 4.0; сохраните эту атрибуцию при использовании.

Файл: https://ftp.pdl.cmu.edu/pub/datasets/twemcacheWorkload/open_source/sample100/cluster7.sort.sample100.zst. Размер около 49 МБ в сжатом виде. Метод выборки sample100 не подтверждён документацией, поэтому показатели не масштабируются на полный кластер. SHA-256 загруженного файла записан в `data/processed.json`; он фиксирует воспроизводимость, а не является опубликованной автором контрольной суммой. Целостность сжатого потока проверяется zstd при полном чтении.

Берутся первые 168 часов от относительного t=0, а не произвольно отобранные удачные пики. Лишний хвост исключён с отчётом. В выбранной неделе 9 695 769 запросов, 44 744 ключа. Сетка 15 минут: 384 интервала train (96 ч), 96 validation (24 ч), 192 test (48 ч). Исходные временные метки относительные; календарные даты и часовой пояс не выдумываются.

## Что именно моделируется

Все get и set одинаково нагружают сервер на один запрос. Ключи преобразуются стабильным BLAKE2b в точный UInt64, затем JCH распределяет их на 2–8 шардов. Число шардов меняется на −1/0/+1 до текущего интервала. Реплик и деления одного горячего ключа между серверами нет.

Живая база определяется только наблюдёнными записями set: последний размер key+value и TTL, истечение удаляет объект. Начальная база пустая, чтения не создают объекты. Трасса не содержит флага успешности операции, поэтому принимается last-write-wins; вытеснение кеша не моделируется. Эта write-defined база — модель размещения, а не реконструкция настоящего содержимого кеша. У выбранной трассы только get/set. Универсальный обработчик других операций содержит упрощения, поэтому другой кластер требует проверки семантики.

На границе интервала миграция считает байты живых объектов, для которых старый и новый JCH отличаются. Включаются все ещё живые объекты предыдущих интервалов; изменения текущего интервала не включаются. Повторное перемещение оплачивается снова. Истечение TTL может уменьшать объём, поэтому сумма миграции не обязана монотонно расти. В отличие от append-only hits_v1 запросы чтения здесь не превращаются в накопленные записи.

Стоимость интервала: `n + 20 * excess / capacity + 4 * moved_bytes / migration_scale`. Capacity — округлённый вверх 75-й перцентиль максимума нагрузки при 4 шардах только на train. Migration scale — медианный объём живой базы на train. Это явно заданный сценарий ограниченного сервера, а не измеренная пропускная способность Twitter или ClickHouse. Превышение считается по каждому шарду, не по среднему. Перенос мгновенный с условным штрафом; нет очередей, времени доставки, сетевой конкуренции, отказов и реальных денежных цен.

## Начальные условия и честность сравнения

Train/validation/test — отдельные эпизоды с исторической живой базой, размещённой по начальной схеме бесплатно. Динамические политики начинают с 2, фиксированные — с их постоянного числа шардов. До старта validation/test доступны последние 4 интервала фактических запросов, размещённых по начальной схеме. Это сравнение политик при заданных начальных условиях, а не непрерывное развёртывание train→test.

Политика видит только уже наблюдённую нагрузку, время суток и текущий объём/цену переноса. Агрегатор знает контрфактическое распределение по всем n, но будущие массивы политике не передаются. Q-learning дискретизирует часть этих признаков; DQN получает все 10 непрерывных признаков. Поэтому разница результатов отражает и представление состояния, а не только нейросеть против таблицы. Состояние неполное, гарантий марковости и оптимальности нет.

Лучшее фиксированное число шардов и пороги выбираются на validation. DQN: 12 предварительных конфигураций × 160 эпизодов, затем 3 финалиста × 3 seed × 400 эпизодов. Веса оптимизируются Adam с Double DQN target, replay и Huber loss. Гиперпараметры выбираются по средней validation cost 3 seed; checkpoint и seed — по validation. Табличный агент: 4 конфигурации × 3 seed × 600 эпизодов. Точная сетка и прочие параметры — в протоколе и ноутбуках. Это ограниченный поиск, не гарантия лучших возможных гиперпараметров.

Test открывается после фиксации выбора в `results/frozen_selection.json`. Три test-результата DQN для выбранной конфигурации публикуются без повторного выбора seed. Offline oracle — отдельная динамическая программа, знающая будущее: только идеальная нижняя граница.

## Файлы

- `data_pipeline.py` — потоковое чтение, TTL, маршрутизация, агрегаты и метаданные.
- `simulator.py` — причинный симулятор, baselines и метрики.
- `agents.py` — табличный агент и нейросеть.
- `experiments.py` — протокол поиска и оценка.
- `tests/` — точность UInt64, TTL/перезапись, переносы, причинность, калибровка, градиенты, Adam, терминальные цели, сохранение весов.
- `results/` — протокол, все испытания, истории, веса, итоговые таблицы и графики.

Большое число повторов одной недели не создаёт новые независимые данные. Для обобщения нужны дополнительные недели/кластеры, для реальной производительности — измерения сервиса. Победа нейросети не предполагается заранее; все результаты сохраняются, включая проигрыши.

## Проверенные результаты

Все пять ноутбуков выполнены. 10 автоматических тестов прошли. Выбранная по validation нейросеть использует 2–5 шардов и на test получает стоимость 779.10 против 929.84 у настроенной пороговой стратегии (ниже на 16.21%). Это экономия в условной модели, сопровождаемая большей перегрузкой: 46 интервалов с превышением против 4 у пороговой стратегии. Полный разбор, все seed и ограничения — в [RESULTS.md](RESULTS.md).

Для точного восстановления окружения этого запуска используйте `requirements-lock.txt` (Python 3.9 на данном Mac). Файл `twitter_sharding_rl.code-workspace` можно открыть через VS Code; он указывает на локальное окружение проекта.
